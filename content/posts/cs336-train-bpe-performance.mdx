这篇文章记录我完成 Stanford CS336 Assignment 1 中 `train_bpe` 的过程。我没有把实现压成一个缺少上下文的大代码块，而是按照数据流拆开关键代码：先看预分词和表示，再看增量索引与 merge 循环，最后进入多进程和 profiling。这样既能看到实际写法，也能解释每个结构为什么存在，以及为什么一个看起来不起眼的陈旧集合，最后占掉了大部分训练时间。

如果想先理解 tokenizer 在语言模型中的位置，可以从本站的 [CS336 第一讲笔记](/posts/cs336-lecture-01-overview-tokenization) 开始；如果想系统复习 UTF-8、BPE 训练与编码，可以继续阅读 [Karpathy Tokenizer 视频笔记](/posts/karpathy-build-gpt-tokenizer)。本文只聚焦一个更工程化的问题：**怎样把 BPE trainer 写对，并让它在完整 TinyStories 语料上跑得足够快。**

## 结果先行

最终实现通过了 `train_bpe` 的正确性、特殊 token 和速度测试。在词表大小为 10,000、特殊 token 为 `<|endoftext|>` 时：

| 语料 | `train_bpe` 时间 | maximum resident set size | 词表大小 | merge 数量 |
| --- | ---: | ---: | ---: | ---: |
| TinyStories validation | 2.541 秒 | 75.36 MiB | 10,000 | 9,743 |
| TinyStories 完整训练集 | 145.602 秒 | 894.17 MiB | 10,000 | 9,743 |

完整训练集的总墙钟时间为 145.79 秒，约 2 分 26 秒；`user + sys` CPU 时间约为 1,005 秒，除以墙钟时间后相当于平均使用约 6.9 个 CPU 核心。运行过程中没有发生 swap。

merge 数量可以直接检查：基础词表包含 256 个单字节 token，再加入 1 个特殊 token，所以需要

$$
10000 - 256 - 1 = 9743
$$

次合并。最终最长的非特殊 token 是 `b' accomplishment'`，长度为 15 bytes。

这组结果不是一次“大改”得到的，而是经过了几轮很具体的测量和修正。

## 先明确训练器应该返回什么

`train_bpe` 的输出有两部分：

```python
vocab: dict[int, bytes]
merges: list[tuple[bytes, bytes]]
```

`vocab` 把整数 token ID 映射到原始字节串；`merges` 按学习顺序记录每次被合并的两个字节片段。内部实现可以使用整数 ID 提高更新效率，但最终接口仍然需要返回 bytes。

训练流程可以概括为：

1. 用 GPT 风格的正则表达式做预分词；
2. 把每个 pre-token 表示成单字节 token 序列；
3. 统计所有相邻 pair 的加权频次；
4. 选择频次最高的 pair，按规定处理并列情况；
5. 只更新真正受到这次合并影响的 pre-token；
6. 重复直到词表达到目标大小。

这里最容易低估的是第三到第五步。朴素实现每轮都扫描整个语料，逻辑直观，却会把大量时间花在重复统计没有变化的内容上。

## 预分词：先把边界处理正确

我的预分词函数返回：

```python
Counter[tuple[bytes, ...]]
```

例如某个 pre-token 编码后是三个字节，它会成为由三个单字节 `bytes` 组成的 tuple；`Counter` 的值则记录它在语料中出现了多少次。这样既保留 byte-level BPE 的语义，也能把重复 pre-token 压缩成一份状态。

特殊 token 必须是硬边界。普通 BPE 不能跨过 `<|endoftext|>` 合并，也不应该把这个字符串当成普通训练文本。因此流程是：先按所有特殊 token 切分文本，再对普通片段运行正则预分词。

这一阶段我逐渐明确了两层表示：

- 预分词接口使用 `tuple[bytes, ...]`，容易检查是否忠实于 UTF-8 字节；
- BPE 内部把每个单字节映射成整数 ID，更新 tuple 时更紧凑。

两种表示并不冲突。关键是让模块边界明确，而不是在整个程序里混用 bytes 和 ID。

### 实际的预分词实现

下面是我实际使用的核心逻辑。特殊 token 会先被 `re.escape`，避免其中的 `|`、`*` 等字符被误当成正则语法；再按长度从长到短排列，防止较短 token 抢先匹配较长 token 的前缀。

```python
from collections import Counter

import regex as re


PAT = (
    r"'(?:[sdmt]|ll|ve|re)"
    r"| ?\p{L}+"
    r"| ?\p{N}+"
    r"| ?[^\s\p{L}\p{N}]+"
    r"|\s+(?!\S)"
    r"|\s+"
)


def pretokenize(
    text: str,
    special_tokens: list[str],
) -> Counter[tuple[bytes, ...]]:
    special_pattern = "|".join(
        re.escape(token)
        for token in sorted(special_tokens, key=len, reverse=True)
    )
    segments = re.split(special_pattern, text) if special_pattern else [text]

    counts: Counter[tuple[bytes, ...]] = Counter()
    for segment in segments:
        for match in re.finditer(PAT, segment):
            encoded = match.group(0).encode("utf-8")
            byte_atoms = tuple(bytes([byte]) for byte in encoded)
            counts[byte_atoms] += 1

    return counts
```

这里不能把整个匹配结果保存成一个 `bytes`，因为 BPE 的初始状态必须仍然是 256 种单字节 token。`tuple(bytes([byte]) for byte in encoded)` 明确表达了这一点。

## 用稳定 word ID 支撑增量更新

为了避免每轮重算所有 pair，我为不同的 pre-token 分配稳定的 `word_id`，并维护下面几组状态：

| 结构 | 含义 |
| --- | --- |
| `word_freq[word_id]` | 这个 pre-token 在语料中的出现次数，训练期间不变 |
| `word_tokens[word_id]` | 这个 pre-token 当前的 token ID 序列 |
| `pair_counts[pair]` | pair 在整个语料中的加权出现次数 |
| `pair_to_words[pair]` | 包含这个 pair 的 `word_id` 集合 |
| `pair_by_counts[count]` | 当前计数等于 `count` 的所有 pair |
| `heap` | 用负计数实现的最大堆，用来快速找到最高频计数 |

其中 `pair_to_words` 是增量算法的核心。选中一个 pair 后，不必扫描所有 pre-token，只需访问真正包含它的 `word_id`。

每次合并遵守同一个不变量：

1. 从全局统计中减去受影响 word 的旧 pair；
2. 在这个 word 内做非重叠合并；
3. 把新 word 的 pair 加回全局统计；
4. 同步更新反向索引和计数桶。

所有增减都必须乘以 `word_freq[word_id]`。例如某个 pre-token 在语料中出现 100 次，其中一个 pair 在这个 pre-token 内出现两次，那么它对全局计数的贡献是 200，而不是 2。

### 非重叠 merge

同一个 token 位置不能同时参加两次合并。因此扫描命中 pair 后要前进两格，否则只前进一格：

```python
def merge(
    ids: tuple[int, ...],
    pair: tuple[int, int],
    new_id: int,
) -> list[int]:
    merged: list[int] = []
    i = 0

    while i < len(ids):
        if (
            i + 1 < len(ids)
            and ids[i] == pair[0]
            and ids[i + 1] == pair[1]
        ):
            merged.append(new_id)
            i += 2
        else:
            merged.append(ids[i])
            i += 1

    return merged
```

例如 `[a, a, a]` 合并 `(a, a)` 后应得到 `[aa, a]`，而不是让中间的 `a` 又参与第二次合并。

### 构建初始 pair 统计和反向索引

预分词 Counter 会被转换成稳定的 word ID。下面这段代码同时构造加权计数和 `pair -> word IDs` 的反向索引：

```python
word_freq: Counter[int] = Counter()
word_tokens: list[tuple[int, ...]] = []

for word, frequency in pretoken_counts.items():
    word_id = len(word_tokens)
    word_freq[word_id] = frequency
    word_tokens.append(tuple(stoi[byte] for byte in word))

pair_counts: Counter[tuple[int, int]] = Counter()
pair_to_words: defaultdict[tuple[int, int], set[int]] = defaultdict(set)

for word_id, frequency in word_freq.items():
    tokens = word_tokens[word_id]
    for pair in zip(tokens, tokens[1:]):
        pair_counts[pair] += frequency
        pair_to_words[pair].add(word_id)
```

这里的 `pair_to_words` 只保存 `word_id` 一次。pair 在一个 word 内出现几次，由遍历旧序列、逐次增减 `pair_counts` 来表达；word 在语料中重复几次，则由 `word_freq` 表达。

### 只更新受影响的 word

选出本轮 pair 后，先复制反向索引快照，因为循环内部会修改原集合。每个受影响 word 都经历“减去旧贡献、完成合并、加回新贡献”：

```python
affected_word_ids = pair_to_words[selected_pair].copy()

for word_id in affected_word_ids:
    frequency = word_freq[word_id]
    old_word = word_tokens[word_id]
    new_word = tuple(merge(old_word, selected_pair, new_id))

    for old_pair in zip(old_word, old_word[1:]):
        old_count = pair_counts[old_pair]
        pair_by_counts[old_count].discard(old_pair)

        pair_counts[old_pair] -= frequency
        new_count = pair_counts[old_pair]
        pair_by_counts[new_count].add(old_pair)
        heappush(heap, -new_count)

        pair_to_words[old_pair].discard(word_id)

    for new_pair in zip(new_word, new_word[1:]):
        old_count = pair_counts[new_pair]
        pair_by_counts[old_count].discard(new_pair)

        pair_counts[new_pair] += frequency
        new_count = pair_counts[new_pair]
        pair_by_counts[new_count].add(new_pair)
        heappush(heap, -new_count)

        pair_to_words[new_pair].add(word_id)

    word_tokens[word_id] = new_word
```

这段代码看起来比每轮重新 `Counter(zip(...))` 复杂，但它把工作量限制在真正包含 `selected_pair` 的 word 上。几个结构必须一起移动：只改 `pair_counts` 而忘记计数桶或反向索引，下一轮就会读取到互相矛盾的状态。

当多个 pair 频次相同时，还要按两个 token 对应的 bytes 做字典序比较。这里比较的是 token 的实际字节内容，而不是内部整数 ID；ID 只代表创建顺序，不能替代题目规定的 tie-breaking。

## 第一次 profiling：`max` 吞掉了大部分时间

早期实现虽然使用了增量 pair 统计，但每轮仍然通过 `max` 扫描整个 `pair_counts`。一次 `cProfile` 中，总计约 38.2 秒，`max` 和它的比较函数累计占用约 28.9 秒，比较函数被调用接近一亿次。

这说明问题不在 `merge` 函数本身，而在“怎样选出下一个 pair”。于是我加入：

- `pair_by_counts[count]`：把相同计数的 pair 放在同一个集合；
- 负数最小堆：快速得到当前最大计数；
- 只在最高计数的集合里做 bytes 字典序比较。

对应的初始化和选择代码如下：

```python
pair_by_counts: defaultdict[int, set[tuple[int, int]]] = defaultdict(set)
for pair, count in pair_counts.items():
    pair_by_counts[count].add(pair)

heap = [-count for count in pair_by_counts]
heapify(heap)

while heap and not pair_by_counts[-heap[0]]:
    heappop(heap)

if not heap:
    # 当前语料中已经不存在可继续合并的 pair
    break

max_count = -heap[0]
selected_pair = max(
    pair_by_counts[max_count],
    key=lambda pair: (vocab[pair[0]], vocab[pair[1]]),
)
```

堆里允许存在旧计数，也就是采用 lazy deletion。真正使用堆顶前，先检查对应计数桶是否仍然非空；空桶对应的旧堆项直接弹出。这样不必为了修改某个 pair 的计数，在堆中搜索并删除任意位置的元素。

这一步也出现过一个很典型的错误：构造出负计数列表后忘记调用 `heapify`。普通列表的第一个元素不保证是最小值，于是第一次 merge 就选错了。速度测试甚至可能通过，但正确性快照会失败。这个经历提醒我：**性能结构首先仍然是正确性结构，任何优化都要立即回到测试验证。**

## 并行预分词：Map、Reduce 和文件偏移

堆优化后，profiling 显示预分词成为主要开销。由于不同文档之间由特殊 token 隔开，可以在这些边界附近切分文件，让多个进程独立统计。

并行流程本质上是一次 Map–Reduce：

```text
文件分块 -> 每个 worker 产生局部 Counter -> 主进程合并 Counter
```

worker 必须定义在模块顶层，因为 macOS 的多进程启动方式需要 pickle 目标函数。任务参数只传路径、起点、终点和特殊 token；每个 worker 自己打开文件。

最容易漏掉的一行是：

```python
with open(input_path, "rb") as file:
    file.seek(start)
    chunk = file.read(end - start)
```

我最初只写了 `read(end - start)`，忘记 `seek(start)`。结果所有进程都从文件开头读取，只是读取长度不同。小语料因为可能只形成一个分块而碰巧通过，包含大量文档边界的 5MB TinyStories 样本则立刻在特殊 token 测试中失败。

完整的 worker 很短：

```python
def _pretokenize_chunk(
    input_path: str,
    start: int,
    end: int,
    special_tokens: list[str],
) -> Counter[tuple[bytes, ...]]:
    with open(input_path, "rb") as file:
        file.seek(start)
        chunk = file.read(end - start)

    text = chunk.decode("utf-8", errors="ignore")
    return pretokenize(text, special_tokens)
```

主进程负责构造任务、选择串行或并行路径，并把每个局部 Counter 合并到总 Counter：

```python
from concurrent.futures import ProcessPoolExecutor, as_completed


def pretokenize_file(
    input_path: str,
    special_tokens: list[str],
    desired_num_chunks: int,
    num_workers: int = 4,
) -> Counter[tuple[bytes, ...]]:
    total_counts: Counter[tuple[bytes, ...]] = Counter()

    with open(input_path, "rb") as file:
        if special_tokens:
            boundary_token = special_tokens[0].encode("utf-8")
            boundaries = find_chunk_boundaries(
                file,
                desired_num_chunks,
                boundary_token,
            )
        else:
            file.seek(0, os.SEEK_END)
            boundaries = [0, file.tell()]

    tasks = [
        (input_path, start, end, special_tokens)
        for start, end in zip(boundaries, boundaries[1:])
    ]

    if num_workers == 1 or len(tasks) == 1:
        for task in tasks:
            total_counts.update(_pretokenize_chunk(*task))
        return total_counts

    with ProcessPoolExecutor(max_workers=num_workers) as executor:
        futures = [
            executor.submit(_pretokenize_chunk, *task)
            for task in tasks
        ]
        for future in as_completed(futures):
            total_counts.update(future.result())

    return total_counts
```

文件边界由课程提供的 `find_chunk_boundaries` 思路确定：先按字节位置估计均匀分块，再向后寻找特殊 token，把边界移动到文档间隙。这样每个 chunk 都能独立预分词，不会把一个普通 pre-token 从中间切开。

另一个重要区分是：

- `desired_num_chunks` 决定有多少个任务；
- `num_workers` 决定最多同时运行多少个进程。

16 个分块和 4 个 worker，含义是每个 worker 依次处理多个任务，而不是启动 16 个进程。若只有 2 个分块，即使设置 8 个 worker，也最多只有两个任务能同时运行。

为了保证并行化没有改变答案，我始终比较完整的 Counter：

```python
assert parallel_counts == serial_counts
```

只比较 `sum(counts.values())` 不够，因为总数相同并不能证明每种 pre-token 的频次都相同。

## 用中位数选择进程数和分块数

单次计时容易受文件缓存、后台任务和进程启动影响。我使用 `time.perf_counter()`，每种配置运行三次并取中位数。

在包含 1,263,131 个 pre-token 的样本上，固定分块策略后得到：

| workers | 中位数 | 相对单进程加速 |
| ---: | ---: | ---: |
| 1 | 1.025 秒 | 1.00× |
| 2 | 0.828 秒 | 1.24× |
| 4 | 0.658 秒 | 1.56× |
| 8 | 0.526 秒 | 1.95× |

固定为 8 个 worker，再比较不少于 worker 数量的分块：

| chunks | 中位数 |
| ---: | ---: |
| 8 | 0.4531 秒 |
| 16 | 0.4566 秒 |
| 32 | 0.4594 秒 |
| 64 | 0.4554 秒 |

这四组相差不超过约 1.4%，已经落入正常波动范围。对当前样本来说，达到 8 个分块后性能基本饱和；继续增加任务只会增加调度与序列化开销。最终我保留 16 个分块，并在本机使用 8 个 worker。这个数字是机器和语料相关的实验结果，不应当被当作所有环境的固定答案。

## 真正的大瓶颈：从未清空的零计数集合

并行预分词完成后，我把 `train_bpe` 分成三个阶段计时：

| 阶段 | 优化前时间 | 占比 |
| --- | ---: | ---: |
| 预分词 | 1.752 秒 | 18.4% |
| 构建初始 pair 状态 | 0.045 秒 | 0.5% |
| merge 循环 | 7.723 秒 | 81.1% |

瓶颈又回到了 merge 循环。我检查计数桶的生命周期后，发现零计数 pair 虽然已从 `pair_counts` 和 `pair_to_words` 删除，却一直留在 `pair_by_counts[0]`：

```python
for pair in pair_by_counts[0]:
    pair_counts.pop(pair, None)
    pair_to_words.pop(pair, None)
```

这段代码每一轮都会重新扫描此前所有已经失效的 pair。随着 merge 增加，零计数集合越来越大，清理本身反而成为主要工作。

修正方式不是让这个循环更快，而是让旧状态只处理一次：

```python
zero_pairs = pair_by_counts.pop(0, set())

for pair in zero_pairs:
    pair_counts.pop(pair, None)
    pair_to_words.pop(pair, None)
```

`pop` 在取出集合的同时删除整个零计数 bucket。以后出现新的零计数 pair 时，`defaultdict(set)` 会创建一个新集合，不会再次带回历史垃圾。

这一处修改后的阶段计时是：

| 阶段 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 预分词 | 1.752 秒 | 1.769 秒 |
| 构建初始状态 | 0.045 秒 | 0.057 秒 |
| merge 循环 | 7.723 秒 | 0.879 秒 |
| 总时间 | 9.523 秒 | 2.708 秒 |

merge 循环约快了 8.8 倍，总时间约快了 3.5 倍。更重要的是，修改后正确性、特殊 token 和速度测试仍然全部通过。

这也是整个实现过程中最有价值的一课：**性能问题不一定来自复杂算法，有时只是某份已经无效的状态没有离开数据结构。**

## 我使用的测量工具

不同工具回答不同问题。

### `time.perf_counter()`：测一段代码经过了多久

```python
from time import perf_counter

start = perf_counter()
vocab, merges = train_bpe(...)
elapsed = perf_counter() - start

print(f"total train_bpe time = {elapsed:.3f}s")
```

它适合比较总时间和阶段时间。绝对返回值没有意义，只有结束值减开始值有意义。

我实际使用的 worker benchmark 会同时检查答案是否一致，并为每种配置取三次运行的中位数：

```python
from pathlib import Path
from statistics import median
from time import perf_counter

from cs336_basics.bpe import pretokenize_file


def measure(input_path: Path, num_workers: int):
    times: list[float] = []
    last_counts = None

    for _ in range(3):
        start = perf_counter()
        counts = pretokenize_file(
            input_path,
            special_tokens=["<|endoftext|>"],
            desired_num_chunks=8,
            num_workers=num_workers,
        )
        elapsed = perf_counter() - start

        print(
            f"workers={num_workers}, "
            f"time={elapsed:.3f}s, "
            f"pretokens={sum(counts.values())}"
        )
        times.append(elapsed)
        last_counts = counts

    print(f"median={median(times):.3f}s, all={times}")
    return last_counts


if __name__ == "__main__":
    input_path = Path("tests/fixtures/tinystories_sample_5M.txt")
    serial_counts = measure(input_path, num_workers=1)

    for num_workers in [2, 4, 8]:
        parallel_counts = measure(input_path, num_workers)
        assert parallel_counts == serial_counts
```

`if __name__ == "__main__"` 在 macOS 上尤其重要。spawn 模式会在子进程中重新导入主模块；如果创建进程池的代码位于模块顶层，就可能递归启动新进程。

### `cProfile`：找到函数级调用热点

`cProfile` 帮我发现早期的 `max` 和比较函数被调用得过于频繁。需要注意，多进程 worker 内部的耗时不会完整显示在主进程 profile 中；它仍然适合分析主进程中的 merge 循环，但并行预分词最好直接测端到端墙钟时间。

### `/usr/bin/time -l`：测墙钟时间和内存

在 macOS 上，我使用：

```bash
/usr/bin/time -l uv run python experiments/train_bpe_tinystories.py
```

其中：

- `real` 是实际等待时间；
- `user` 是所有 CPU 执行用户代码的累计时间，多进程时可以明显大于 `real`；
- `sys` 是内核态累计时间；
- `maximum resident set size` 在这里按字节报告，除以 $1024^2$ 得到 MiB。

并行进程下，这个 maximum RSS 数字不应简单理解成所有 worker 同一时刻内存的总和，因此报告结果时也应该保留测量命令和指标名称。

## 更新：从 BPE trainer 走到可训练的二进制语料

前面的版本停在“学出 `vocab` 和 `merges`”。这还不是语言模型真正读取的数据。完整链路还要继续经过四步：

```text
原始 UTF-8 文本
  -> train_bpe 学习 vocab / merges
  -> Tokenizer 用 merge rank 编码新文本
  -> 流式写出 uint16 token ID
  -> 用 memmap 读取并抽样训练 batch
```

这一节补全后，`train_bpe` 不再是孤立函数，而是已经接上了 Transformer 训练的数据入口。

### 为什么把 bytes 保存成十六进制 JSON

词表中的值是任意 `bytes`，其中可能包含不可打印字节，也未必能单独解码成合法 UTF-8。直接把它们当字符串写入 JSON 会丢失信息。因此我把每个 token 序列化为十六进制字符串：

```python
vocab_data = {
    str(token_id): token_bytes.hex()
    for token_id, token_bytes in vocab.items()
}
merges_data = [
    [left.hex(), right.hex()]
    for left, right in merges
]

vocab_path.write_text(
    json.dumps(vocab_data),
    encoding="utf-8",
)
merges_path.write_text(
    json.dumps(merges_data),
    encoding="utf-8",
)
```

读取时做完全可逆的反变换：

```python
raw_vocab = json.loads(vocab_path.read_text(encoding="utf-8"))
vocab = {
    int(token_id): bytes.fromhex(token_hex)
    for token_id, token_hex in raw_vocab.items()
}

raw_merges = json.loads(merges_path.read_text(encoding="utf-8"))
merges = [
    (bytes.fromhex(left), bytes.fromhex(right))
    for left, right in raw_merges
]
```

十六进制会让 JSON 比原始 bytes 更大，但 tokenizer 文件只加载一次，而且这种表示简单、无歧义、容易人工检查。

### 编码不是“把所有可合并 pair 一起合并”

训练得到的 `merges` 是有顺序的。越早学到的 pair，rank 越小，编码时优先级越高：

```python
self.merge_ranks = {
    pair: rank
    for rank, pair in enumerate(merges)
}
```

对一个 pre-token 编码时，先把 UTF-8 拆成单字节 pieces，然后反复完成：

1. 查看当前所有相邻 pair；
2. 找到 rank 最小、也就是训练时最早出现的 pair；
3. 从左到右非重叠地合并这个 pair；
4. 重新观察新的相邻关系，直到再也没有已知 pair。

实际实现如下：

```python
def _apply_merges(self, pieces: list[bytes]) -> list[bytes]:
    while True:
        min_rank = float("inf")

        for pair in zip(pieces, pieces[1:]):
            rank = self.merge_ranks.get(pair, float("inf"))
            min_rank = min(min_rank, rank)

        if min_rank == float("inf"):
            break

        pair = self.merges[min_rank]
        merged_bytes = pair[0] + pair[1]
        new_pieces: list[bytes] = []
        i = 0

        while i < len(pieces):
            if (
                i + 1 < len(pieces)
                and (pieces[i], pieces[i + 1]) == pair
            ):
                new_pieces.append(merged_bytes)
                i += 2
            else:
                new_pieces.append(pieces[i])
                i += 1

        pieces = new_pieces

    return pieces
```

我曾经写过下面这种条件：

```python
self.merge_ranks[(pieces[i], pieces[i + 1])] == min_rank
```

它有两个问题。第一，当前 pair 可能根本不在字典里，直接索引会抛出 `KeyError`；第二，真正需要合并的是本轮已经选定的 `pair`，直接比较 `(pieces[i], pieces[i + 1]) == pair` 更明确，也不会再次把“查 rank”和“执行 merge”混在一起。

### 特殊 token 为什么要先保留下来

普通文本使用 GPT 风格正则预分词；特殊 token 则必须整体变成一个 ID，不能送入普通 BPE。带捕获组的 `re.split` 会把分隔符也保留在结果中：

```python
sorted_special_tokens = sorted(
    self.special_tokens,
    key=len,
    reverse=True,
)
pattern = "|".join(
    re.escape(token)
    for token in sorted_special_tokens
)
segments = re.split(f"({pattern})", text)
```

假设文本是：

```text
first<|endoftext|>second
```

结果会近似是：

```python
["first", "<|endoftext|>", "second"]
```

遍历时，特殊 token 直接查 `token_to_id`；其他片段才调用普通编码：

```python
for segment in segments:
    if not segment:
        continue
    if segment in special_token_set:
        ids.append(self.token_to_id[segment.encode("utf-8")])
    else:
        ids.extend(self._encode_normal_text(segment))
```

这里按长度降序排列和训练预分词时理由相同：若多个特殊 token 存在前缀关系，应当先匹配更长的那个。

### 解码为何最后才处理 UTF-8

一个 token 的 bytes 不保证能独立解码。例如 `é` 的 UTF-8 是 `b'\xc3\xa9'`，单独解码 `b'\xc3'` 会失败。正确顺序是先把所有 token bytes 拼起来，再统一解码：

```python
def decode(self, ids: list[int]) -> str:
    token_bytes = b"".join(self.vocab[token_id] for token_id in ids)
    return token_bytes.decode("utf-8", errors="replace")
```

`errors="replace"` 让任意 ID 序列都有定义良好的输出；对合法文本的 `encode -> decode` 往返，不会产生替换字符。

### Unicode、编码与 NUL：三个容易混淆的层次

Python 的 `str` 表示 Unicode 字符序列，`bytes` 表示原始字节序列，token ID 则只是词表索引。这三层不能混用。

例如 NUL 字符：

```python
nul = "\x00"

print(repr(nul))  # '\x00'
print(ord(nul))   # 0
print(len(nul))   # 1
```

终端打印 `A\x00B` 时，中间通常看不见，但它仍然存在：

```python
text = "A\x00B"

assert len(text) == 3
assert text.index("\x00") == 1
assert text.encode("utf-8") == b"A\x00B"
```

“打印不出来”不等于“字符串中没有”。调试控制字符要使用 `repr()`、`len()`、`ord()` 和 `.encode()`，不能只相信终端视觉结果。

不同编码也会产生完全不同的字节长度：

| 文本 | UTF-8 | UTF-16-LE | UTF-32-LE |
| --- | ---: | ---: | ---: |
| `hello` | 5 bytes | 10 bytes | 20 bytes |
| `你好` | 6 bytes | 4 bytes | 8 bytes |
| `🙃` | 4 bytes | 4 bytes | 4 bytes |

Byte-level BPE 使用的是 UTF-8 bytes，不是“一个 Unicode 字符一个 token”。中文字符通常由 3 个 UTF-8 bytes 组成，emoji 常由 4 个或更多 bytes 组成；训练出的 merge 才可能把这些字节重新组合成更长 token。

最重要的不变量是：**不要逐 token 做 UTF-8 解码。** `é` 的 UTF-8 bytes 为：

```python
b"\xc3\xa9"
```

若两个 BPE token 恰好分别存 `b"\xc3"` 和 `b"\xa9"`，单独解码任何一个都不完整；先拼接才会得到合法的 `é`。类似地，`b"\xc3("` 是真正的无效 UTF-8，因为 `0xc3` 后面缺少合法 continuation byte。二者的区别是：前者只是被 token 边界暂时切开，后者拼接后仍然非法。

### 特殊 token 与普通文本为什么必须分两条路径

特殊 token 是 tokenizer 协议的一部分，而不是一个“碰巧长得特殊”的普通字符串。训练时它阻止 pair 跨文档边界；编码时它必须整体映射成指定 ID；解码时它再按词表 bytes 还原。

因此通用实现不能把 `<|endoftext|>` 写死在 `pretokenize_file` 内。函数应该接收 `special_tokens`，按长度降序构造转义后的模式，并让调用方决定哪些特殊 token 生效。这样 TinyStories 使用一个边界 token，未来有多个特殊 token 时仍然保持同一接口。

### 压缩率与吞吐量分别回答什么

压缩率使用 bytes/token：

$$
\text{bytes per token}
=\frac{\text{UTF-8 bytes}}{\text{token count}}.
$$

数值越大，表示平均一个 token 覆盖的原始字节越多。但它不是“越大永远越好”：词表更大需要更大的输出层，而且跨域 tokenizer 的切分行为也可能不同。

我用固定随机种子的 reservoir sampling 抽取文档，避免只取文件开头；吞吐量先预热，再重复三轮取中位数。实测结果是：

| tokenizer / 文本 | bytes/token |
| --- | ---: |
| TinyStories tokenizer / TinyStories | 4.0645 |
| OWT tokenizer / OWT | 4.3483 |
| TinyStories tokenizer / OWT | 3.2405 |

OWT tokenizer 的编码吞吐量为约 `739,118 bytes/s`。若简单线性外推到 825 GB 的 Pile，单进程约需 12.92 天。这个估算不是实际生产承诺，因为磁盘、文档长度分布、并行度和机器都会改变结果；它的作用是尽早说明“完整语料不能靠一次随手运行解决”。

### 为什么二进制文件选择小端 `uint16`

TinyStories 词表有 10,000 项，OWT 词表有 32,000 项，token ID 都小于 $2^{16}=65536$。因此每个 ID 可以固定占 2 bytes：

```python
if min_id < 0 or max_id >= 2**16:
    raise ValueError(
        f"Token IDs must fit uint16, got range {min_id}–{max_id}"
    )

np.asarray(ids, dtype="<u2").tofile(output_file)
```

`<u2` 的含义是：

- `<`：little-endian，小端；
- `u`：unsigned integer，无符号整数；
- `2`：每个元素 2 bytes。

固定端序比依赖机器原生端序更利于复现。以后读取时要使用同一个 dtype：

```python
dataset = np.memmap(path, dtype="<u2", mode="r")
```

不能为了省空间直接写 `uint16` 而不检查 ID 范围；否则词表超过 65,536 时会发生静默截断，文件仍能生成，但训练数据已经损坏。

### 流式切分避免把整份 OWT 放进内存

原始文件用 `<|endoftext|>` 分隔文档。每次读取 1 MiB 时，特殊 token 可能横跨两个 chunk，所以必须保留末尾未完成的 `buffer`：

```python
def iter_text_segments(
    path,
    special_token="<|endoftext|>",
    chunk_size=1024 * 1024,
):
    buffer = ""

    with open(path, encoding="utf-8") as file:
        while chunk := file.read(chunk_size):
            buffer += chunk
            pieces = buffer.split(special_token)

            for document in pieces[:-1]:
                yield document
                yield special_token

            buffer = pieces[-1]

    if buffer:
        yield buffer
```

`pieces[:-1]` 都已经由完整分隔符终止，可以安全交给 tokenizer；`pieces[-1]` 可能只是下一篇文档的前半段，必须留到下一轮。特殊 token 也重新 `yield`，否则文档边界会从训练序列里消失。

编码器只保留一个 segment 的 ID，然后立刻写盘：

```python
def encode_dataset(tokenizer, input_path, output_path):
    min_id = min(tokenizer.vocab)
    max_id = max(tokenizer.vocab)

    if min_id < 0 or max_id >= 2**16:
        raise ValueError("token IDs do not fit uint16")

    total_tokens = 0

    with open(output_path, "wb") as output_file:
        for segment_index, segment in enumerate(
            iter_text_segments(input_path),
            start=1,
        ):
            ids = tokenizer.encode(segment)

            if ids:
                np.asarray(ids, dtype="<u2").tofile(output_file)
                total_tokens += len(ids)

            if segment_index % 10_000 == 0:
                print(
                    f"{output_path.name}: "
                    f"{segment_index} segments, "
                    f"{total_tokens} tokens",
                    flush=True,
                )

    return total_tokens
```

### 临时文件让“存在”真正表示“已完成”

长任务如果直接写最终文件名，中途退出也会留下一个看似存在、实际不完整的 `.bin`。下次脚本若只用 `output_path.exists()` 判断，就会错误跳过它。

我的批处理先写 `.bin.tmp`，完成后再原子替换为正式文件：

```python
temporary_path = output_path.with_suffix(".bin.tmp")

total_tokens = encode_dataset(
    tokenizer,
    input_path,
    temporary_path,
)

temporary_path.replace(output_path)
```

这样正式 `.bin` 只在完整编码成功后出现。任务结束时还要检查没有残留 `.tmp`，不能仅凭最后一条日志判断完成。

### 四份语料的最终结果

四个文件已经全部完成：

| 文件 | token 数 | 文件字节数 | 编码时间 | token ID 范围 |
| --- | ---: | ---: | ---: | ---: |
| `tinystories_train.bin` | 541,229,347 | 1,082,458,694 | 2,781.191 秒 | 9–9,999 |
| `tinystories_valid.bin` | 5,465,883 | 10,931,766 | 24.354 秒 | 10–9,999 |
| `owt_train.bin` | 2,727,120,452 | 5,454,240,904 | 12,652.514 秒 | 10–31,999 |
| `owt_valid.bin` | 66,401,098 | 132,802,196 | 269.999 秒 | 10–31,999 |

合计是 **3,340,216,780 tokens**。整批长任务的墙钟时间为 15,703.95 秒，也就是约 4 小时 21 分 44 秒；`maximum resident set size` 为 172,376,064 bytes，约 164.39 MiB。

每个文件都满足一个非常有力的结构检查：

$$
\text{file bytes}=2\times\text{token count}.
$$

例如 OWT train：

$$
2\times2{,}727{,}120{,}452
=5{,}454{,}240{,}904.
$$

最终核验不只看文件大小，还包括：

1. 四个正式文件全部存在；
2. 没有遗留 `.tmp`；
3. 都能以 `np.memmap(..., dtype="<u2")` 打开；
4. 完整扫描所得最小、最大 ID 都落在各自词表范围；
5. token 数等于文件大小除以 2。

到这里，tokenizer 阶段才算真正闭环：不是“程序打印了 completed”，而是训练产物、编码语义、文件格式和消费者读取方式彼此一致。

## 这次实现留下的几个方法论

### 1. 先定义不变量，再谈优化

我反复检查的不是“代码看起来是否合理”，而是一些可验证的不变量：特殊 token 不参与普通合并、pair 计数必须乘 word 频率、并列时比较 bytes、串并行 Counter 完全相同、优化前后的 merges 完全相同。

### 2. 每次只改一个主要变量

进程数实验固定分块策略，分块数实验固定 worker 数；阶段计时确认瓶颈后，才修改零计数 bucket。否则看到一个更快的数字，也很难知道究竟是哪项变化起作用。

### 3. 数据结构的生命周期和类型同样重要

选择 `Counter`、反向索引、计数桶和堆只是第一步。还必须持续回答：谁创建它、谁更新它、什么时候删除旧状态、它是否仍然表达当前事实。`pair_by_counts[0]` 的问题正是生命周期错误，而不是容器类型错误。

### 4. 并行化必须同时证明正确性和收益

多个 worker 能更快完成 regex 预分词，但也引入文件偏移、pickle、进程启动、任务数量和汇总内存等新问题。只有同时满足“结果完全相同”和“重复测量确实更快”，并行化才算完成。
