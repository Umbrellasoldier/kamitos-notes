**覆盖范围说明：** 本文已逐段对照官方 `lecture_01.py`，覆盖课程动机、语言模型发展、可执行讲义与课程规则、五个课程模块、分词对比、BPE 训练与编码。讲义中用于列举历史的每一篇模型论文没有逐篇复述；我只对会改变本讲理解的链接补充结论，并在文末保留继续阅读入口。因此它是一份完整的课程笔记，而不是讲义的逐字转写。

## 一页总结

如果只记住这一讲的五件事，我会选择下面这些：

1. **CS336 的目标不是调用一个大模型，而是拆掉抽象层，亲手实现并训练语言模型。**
2. **整门课的主线是固定资源下的效率。** 模型结构、系统、数据与缩放规律，最终都在回答“如何把有限算力变成更好的模型”。
3. **分词是计算分配策略。** 它不仅决定文本如何编号，也决定序列长度、注意力成本和词表参数量。
4. **字符、字节和单词方案各有明显缺陷；BPE 在覆盖率、压缩率和词表规模之间提供了实用折中。**
5. **真正理解 BPE，要同时掌握训练与编码。** 训练阶段学习有序的合并规则，编码阶段只能应用这些已经学到的规则。

## 为什么还要“从头构建”语言模型

现代模型 API 已经把推理、微调乃至智能体封装得很方便。但抽象层总会泄漏：当训练不稳定、吞吐不足、显存超限，或研究问题落在接口能力之外时，只会调用 API 并不足以解释和解决问题。

CS336 因此选择了一个非常直接的学习哲学：**通过构建来理解**。课程不要求我们复刻前沿模型的规模，而是希望沉淀三类可以迁移的能力：

- **机制**：理解 Transformer、优化器、并行训练与推理系统怎样工作；
- **方法**：认真核算计算、显存和通信，把硬件利用率当作模型质量的一部分；
- **直觉**：知道数据、模型规模与训练预算的选择会怎样影响最终效果。

讲义把模型能力写成一个很有启发性的关系：

$$
\text{accuracy} \approx \text{efficiency} \times \text{resources}.
$$

资源更多当然有帮助，但研究和工程能直接改进的往往是效率。在计算与数据预算固定时，效率更高，才有机会训练出更好的模型。

这也比“规模就是一切”更准确地解释了 **The Bitter Lesson**：真正长期有效的是能够随计算规模扩展的方法，而不是简单地把更多计算投入任意方法。[算法效率研究](https://arxiv.org/abs/2005.04305)提供了一个直观例子：2012 到 2019 年间，在 ImageNet 上达到 AlexNet 水平所需的训练计算减少约 44 倍；同期硬件和算法的改进是相乘关系。这项结果来自视觉任务，不能直接当成语言模型定律，但它很好地说明了为什么“效率”本身就是进步来源。

### 小模型为什么不能完整代表前沿模型

前沿模型训练昂贵，而且公开技术细节有限；课堂只能在较小规模上完成实验。问题是，尺度改变时，系统瓶颈和模型行为也可能改变：

- 注意力与 MLP 占总 FLOPs 的比例会随模型形状和上下文长度变化；
- 某些任务在小模型上几乎没有进展，扩大规模后才出现明显能力，[涌现能力论文](https://arxiv.org/abs/2206.07682)把这种现象定义为无法从较小模型表现直接外推的能力；不过[后续研究](https://arxiv.org/abs/2304.15004)指出，非连续评价指标也可能制造“突然出现”的表象，因此这里更适合把它理解为外推风险，而不是已经确定的尺度机制；
- 在小实验中有效的数据配比或结构选择，不保证原样迁移到更大规模。

![八项任务的表现随训练计算量增加而变化，其中多项任务在较大规模才出现明显提升](/posts/cs336-lecture-01-overview-tokenization/wei-emergence-plot.png)

*图：第一讲用这组曲线说明小模型表现未必能平滑外推到大模型；曲线也应结合评价指标是否连续来解读。来源：[Stanford CS336 第一讲讲义](https://cs336.stanford.edu/lectures/?trace=lecture_01)。*

因此，课程强调的“机制”和“效率思维”迁移性较强，而具体设计直觉只能部分迁移。我们仍然要做小实验，但要知道结论的适用范围。

### 课程适合谁，也不解决什么

这是 Stanford 的 5 学分高强度课程，共五次作业。第一讲甚至引用往届反馈来提醒：仅第一次作业的工作量就非常大。它适合想拆开底层机制、锻炼研究工程能力的人；如果目标是快速把现成模型用于某个业务领域，直接提示或微调通常更合适。

课程也不是热门技术名词的巡礼。多模态、RAG 等主题不是这一版的重点，它更关心能够长期复用的基础：训练、系统、缩放、数据与对齐。

## 从语言模型历史看今天的技术栈

第一讲快速回顾了语言模型的发展。重点不是背年份，而是辨认今天系统中的各个部件来自哪里：

- 从 Shannon 的信息论、n-gram，到神经语言模型与 LSTM；
- 从 seq2seq、Adam、注意力，到奠定现代架构的 Transformer；
- 从 ELMo、BERT、T5，到 GPT 系列推动上下文学习与规模化；
- 从缩放规律、PaLM、Chinchilla，到对参数量、数据量和计算量的系统配比；
- 从早期开放模型，到 Llama、Mistral、DeepSeek、Qwen 等开放权重模型；
- 从“下载后微调”和“通过提示调用”，走向能够使用工具并执行任务的智能体。

产品形态变化很快，但底层问题没有消失：注意力如何计算，内核怎样访问内存，优化是否稳定，数据是否值得消耗计算。长上下文和智能体只是让这些基础问题以新的约束重新出现。

讲义还特意区分了两种常被混用的“开放”：**开放权重**通常表示权重和论文可得；更完整的**开放开发或开放源码模型**还会公开训练代码、数据及过程，课程以 OLMo、Nemotron、Marin 为例。开放权重能提高可定制性和研究可达性，但不等于训练过程完全透明；[开放基础模型的社会影响研究](https://arxiv.org/abs/2403.07918)也同时讨论了创新、竞争、透明度收益以及监测和滥用风险。

## 课程的五块拼图

CS336 将从头训练语言模型拆成五个相互咬合的模块：

| 模块 | 核心问题 | 代表内容 |
| --- | --- | --- |
| 基础 | 一个语言模型最少需要什么 | 分词、Transformer、交叉熵、AdamW、训练循环 |
| 系统 | 如何把硬件真正用起来 | 内核、FlashAttention、分布式并行、推理优化 |
| 缩放规律 | 大实验开始前怎样做决策 | 小规模实验、曲线拟合、预算外推、超参数选择 |
| 数据 | 哪些 token 值得拿来训练 | 收集、清洗、去重、过滤、混合与合成数据 |
| 对齐 | 怎样让模型遵循人的意图 | 偏好数据、奖励信号、PPO、DPO、GRPO |

### 1. 基础：模型由哪些选择组成

第一单元的目标是独立训练一个基本语言模型，内容不止 Transformer 本身：

- **分词**决定模型操作的“原子”；
- **架构**从原始 Transformer 出发，再考察 SwiGLU、RoPE、RMSNorm、QK-Norm、稀疏注意力、GQA、MLA、MoE，以及 Mamba 一类状态空间或循环替代方案；
- **训练**涉及损失函数、AdamW 等优化器、初始化、学习率日程、正则化、批大小与 MoE 负载均衡。

这些选择最终要平衡三个目标：**表达能力**足以拟合复杂依赖，**稳定性**让参数和梯度处于合理范围，**效率**则要求训练与推理都能在硬件上跑得足够快。

![语言模型的 Transformer 堆叠结构，以及单个 pre-norm Transformer block 的内部组成](/posts/cs336-lecture-01-overview-tokenization/transformer-architecture.png)

*图：从 token 与位置嵌入开始，经过多层因果自注意力和前馈网络，再由归一化与输出层得到 token 概率。来源：[Stanford CS336 第一讲讲义](https://cs336.stanford.edu/lectures/?trace=lecture_01)。*

第一次作业会实现 BPE、Transformer、交叉熵、AdamW 与训练循环，完成资源核算，并在 TinyStories 和 OpenWebText 上训练。讲义给出的排行榜目标是在一张 B200、45 分钟预算内尽量降低 OpenWebText 困惑度。

### 2. 系统：瓶颈常常是搬运而非计算

系统单元从资源核算开始。训练参数量为 $N$、token 数为 $D$ 的稠密 Transformer 时，常用 $C\approx6ND$ 估计前向与反向计算；例如 70B 参数、1T token 的量级约为 $4.2\times10^{23}$ FLOPs。

但理论 FLOPs 不等于真实速度。参数需要从 HBM 搬到计算单元，Roofline 分析用算术强度判断任务是受计算吞吐还是内存带宽限制。优化的核心原则是少搬数据：

![内存与计算单元之间由有限带宽连接的数据搬运示意图](/posts/cs336-lecture-01-overview-tokenization/compute-memory.png)

*图：计算单元再快，也要等待参数和激活从内存送达；这条窄通道正是许多算子的实际瓶颈。来源：[Stanford CS336 第一讲讲义](https://cs336.stanford.edu/lectures/?trace=lecture_01)。*

- 用算子融合把多次“读—算—写”压成一次数据往返；
- 用 tiling 让数据块留在更快的片上存储中，FlashAttention 是代表性案例；
- 用 profiling 验证 warp divergence、内存合并访问、bank conflict 与 occupancy 等实际瓶颈；
- 多卡训练还要在数据、张量、流水线、序列和专家并行之间选择，并控制 gather、reduce、all-reduce 的通信代价。

第二次作业对应这些概念：用 Triton 写融合 RMSNorm，完成分布式数据并行和优化器状态切分，再对实现做基准测试与性能分析。讲义推荐的延伸读物是 [How to Scale Your Model](https://jax-ml.github.io/scaling-book/)。

### 3. 缩放规律：先设计 scaling recipe

完整规模上的超参数搜索过于昂贵。课程把问题从“为一个模型找参数”改写为构造 **scaling recipe**：给定 FLOPs，输出模型规模、数据量和其他超参数。

具体做法是在多个较小预算上运行实验、拟合损失曲线，再外推目标规模。ISOFLOP 曲线则在每个固定计算预算下寻找最优参数量。这里最关键的判断是：**可预测性至少和单点最优同样重要**；如果小实验不能稳定预测大实验，就无法放心投入昂贵训练。第三次作业会提供一个“超参数到损失”的训练接口，要求收集数据点、拟合规律，并提交外推的超参数和损失预测。

![Chinchilla 的 ISOFLOP 曲线，以及由较小计算预算外推参数量和训练 token 数的缩放关系](/posts/cs336-lecture-01-overview-tokenization/chinchilla-isoflop.png)

*图：左侧先在每个固定 FLOPs 预算下寻找损失最低点，中、右两图再把这些最优点拟合成参数量和训练 token 数的缩放规律。来源：[Stanford CS336 第一讲讲义](https://cs336.stanford.edu/lectures/?trace=lecture_01)。*

### 4. 数据：先定义能力，再决定训练什么

数据单元先区分两类评测：

- **内部评测**服务于模型迭代，关注不同规模上的平滑趋势和相对改进；
- **外部评测**服务于真实使用场景，关注绝对质量与生态有效性。

困惑度适合做连续、低噪声的内部信号，但评测语料最好不在公开训练数据中，以减少污染。GPQA、HLE、SWE-bench、Terminal-Bench 等更接近具体能力，却也无法用单一分数代表通用模型。

原始网页、书籍、论文和代码还不是可直接训练的文本。数据管线需要完成正文抽取、质量与安全过滤、去重、数据源混合以及合成或重写；其中去重既节省计算，也降低记忆训练样本的风险。课程进一步区分大而多样的预训练数据、高质量和长上下文导向的中期训练数据，以及对话和工具轨迹等后训练数据。第四次作业会把 Common Crawl HTML 转成文本，训练过滤器，并用 MinHash 去重。

讲义也把版权与授权视为数据工程的一部分，而不是下载完成后的附注。它链接的 [Foundation Models and Fair Use](https://arxiv.org/abs/2303.15715)梳理了美国合理使用框架，并强调合理使用并非自动成立；当模型输出与受版权保护内容高度相似、又影响原内容市场时，风险会变化。论文主张让技术缓解措施与法律政策共同演进。这里记录的是论文与课程提出的问题，不构成法律意见。

### 5. 对齐：当评价比生成容易

预训练提供的是逐 token 的完整监督，对齐则利用较弱但更容易获得的信号：先让模型生成候选回答，再由人类、验证器或模型裁判评分，最后让模型更偏好高分结果。

PPO 把问题放在强化学习框架中；DPO 直接从偏好对优化策略，流程更简洁；GRPO 用组内相对奖励避免单独训练价值模型。挑战不只在算法：大规模在线采样需要异步推理基础设施，还要在样本的新鲜程度、训练稳定性和系统吞吐之间权衡。第五次作业会实现 DPO 与 GRPO。

这五块并不是独立章节，而是在争夺同一份资源预算。例如，训练计算量常用下面的近似式做第一步估算：

$$
C \approx 6ND,
$$

其中 $N$ 是模型参数量，$D$ 是训练 token 数量。这个式子不包含所有实现细节，却足以暴露一个基本取舍：预算不变时，模型更大意味着可训练的数据更少，反之亦然。

[Kaplan 等人的缩放规律](https://arxiv.org/abs/2001.08361)发现，交叉熵损失会随模型规模、数据量和训练计算呈稳定的幂律变化，并据此讨论固定预算的最优分配。[Chinchilla](https://arxiv.org/abs/2203.15556)进一步指出，当时不少大模型相对数据量而言训练不足，参数量和训练 token 应更协调地增长。第一讲给出的粗略经验是 $D\approx20N$，但这不是永远适用的神奇常数：它来自特定模型、数据和训练设定，也没有纳入后续推理成本；若部署成本重要，更小的模型配合更多训练数据可能拥有更好的全生命周期成本。

## 效率是贯穿课程的主线

讲义把资源拆成数据与硬件，而硬件瓶颈又可以继续拆成计算、内存和通信。

这套视角可以把看似无关的课程内容统一起来：

- **分词**压缩原始字节，减少 Transformer 需要处理的序列长度；
- **模型结构**减少不必要的参数、激活或浮点运算；
- **高性能内核**通过融合与分块，减少昂贵的数据搬运；
- **并行策略**在多张加速卡之间分配计算，同时控制通信开销；
- **数据治理**过滤低价值样本，避免把算力花在重复或劣质 token 上；
- **缩放规律**用便宜的小实验预测昂贵的大实验，降低试错成本。

推理阶段也有两种不同瓶颈：处理整段输入的 **prefill** 通常更偏计算密集，而逐 token 生成的 **decode** 往往更受内存带宽限制。量化、蒸馏、推测解码、连续批处理等技术，都是在针对不同瓶颈重新安排资源。推测解码的关键是让便宜的草稿模型先提出多个候选，再由完整模型并行验证；校正正确时，它提升速度但不改变目标模型的采样分布。

![语言模型推理中的 prefill 与逐 token decode 两个阶段，以及贯穿两阶段的 KV cache](/posts/cs336-lecture-01-overview-tokenization/prefill-decode.png)

*图：prefill 可以并行处理整段输入，decode 则依赖已经生成的 token 逐步推进；KV cache 避免每一步重复计算过去的键和值。来源：[Stanford CS336 第一讲讲义](https://cs336.stanford.edu/lectures/?trace=lecture_01)。*

## 分词究竟在做什么

语言模型不能直接接收字符串。Tokenizer 需要完成双向映射：

$$
\text{bytes} \xrightarrow{\operatorname{encode}} (t_1,t_2,\ldots,t_T)
\xrightarrow{\operatorname{decode}} \text{bytes}.
$$

最重要的正确性条件是往返不丢信息：

$$
\operatorname{decode}(\operatorname{encode}(x))=x.
$$

实际系统通常先把文本编码成 UTF-8 字节，再把一段或多段字节映射为整数 token。于是 tokenizer 同时承担了三件事：

1. 给所有输入提供稳定的整数表示；
2. 压缩序列，让模型少走一些时间步；
3. 决定模型在哪些文本片段上分配独立的嵌入和预测能力。

![把 Stanford was founded in 1885 这句话编码成带有不同文本片段边界的 token ID，并能解码回原文](/posts/cs336-lecture-01-overview-tokenization/tokenized-example.png)

*图：tokenizer 的 encode 把文本切成 token 并映射为整数，decode 再把整数序列无损还原为文本。来源：[Stanford CS336 第一讲讲义](https://cs336.stanford.edu/lectures/?trace=lecture_01)。*

观察现成 tokenizer 时，会看到一些不太像“词”的现象：词前空格可能属于 token；同一个词出现在词首和词中可能被切成不同形式；长数字也常被分成几位一组。这提醒我们，token 是由训练数据和算法共同学到的计算单元，不等同于语言学意义上的单词。

讲义用 OpenAI 的 [`tiktoken`](https://github.com/openai/tiktoken) 和 `o200k_base` 编码演示 `Hello, 🌍! 你好!`。下面这段代码可以直接检查往返性质；也可以在讲义推荐的 [Tiktokenizer](https://tiktokenizer.vercel.app/) 中切换编码器，观察空格、中文、emoji 和数字怎样被切分。

```python
import tiktoken

encoding = tiktoken.get_encoding("o200k_base")
text = "Hello, 🌍! 你好!"
token_ids = encoding.encode(text)

assert encoding.decode(token_ids) == text
print(token_ids)
```

`tiktoken` 对 BPE 的总结也补足了课堂直觉：它可逆、能处理训练词表之外的任意文本、通常能把字节序列压短，并倾向于让常见子词反复出现在不同上下文中。后一点并不保证 token 一定符合语言学边界，但能让模型复用统计规律。

### 压缩率为何重要

第一讲用下面的量衡量 tokenizer 的压缩效果：

$$
r=\frac{\text{UTF-8 字节数}}{\text{token 数}}.
$$

$r$ 越大，同样文本产生的 token 越少。若 1000 字节文本被编码成约 250 个 token，那么压缩率约为 4。

更短的序列会减少训练和推理步数，而且标准注意力对序列长度 $T$ 的主要计算与存储开销近似按 $T^2$ 增长。因此，分词方式会真实地影响模型能容纳多少上下文，以及一次训练需要多少资源。

但词表也不能无限扩大。每新增一个 token，嵌入层和输出层都要增加相应参数；过于稀有的 token 又很难学好。分词的核心权衡可以概括为：

> 用可控的词表规模，换取尽可能短且有统计价值的序列。

## 四种分词方案的权衡

Python 字符串可看作 Unicode 码点序列，`ord("a") == 97`，而 `ord("🌍") == 127757`。换成 UTF-8 后，ASCII 字符 `a` 占 1 字节，`🌍` 占 4 字节，常见汉字通常占 3 字节。字符方案直接面对约十几万个码点；字节方案把基础词表固定为 256，却会把多字节字符和常见词都展开为更长序列。

| 方案 | 优点 | 主要问题 |
| --- | --- | --- |
| 字符 | 直观，接近人对文字的认识 | Unicode 字符是十万量级，词表大且分布极不均匀 |
| 字节 | 只需 256 个基础符号，可覆盖任意 UTF-8 文本，没有未知字符 | 压缩率恒为 1，序列太长 |
| 单词 | 对常见自然语言有较好压缩率，语义边界直观 | 词表近乎无界，未登录词和形态变化难处理 |
| BPE | 保留字节级全覆盖，并从数据中学习常见片段 | 需要训练词表；边界受语料、预切分和实现细节影响 |

字符、字节、单词分别把粒度固定在不同位置，而 **Byte Pair Encoding（BPE）** 让粒度由数据决定：罕见片段可以退回到字节，常见片段则逐步合并成更长的 token。

## 从字节开始推导 BPE

BPE 最早由 Philip Gage 在 1994 年作为通用数据压缩方法提出；[Sennrich、Haddow 与 Birch](https://arxiv.org/abs/1508.07909)在神经机器翻译中把它改造成子词方案，用较小单元表示稀有词和未登录词，并在当时的英德、英俄翻译实验中分别比回退词典基线提升 1.1 和 1.3 BLEU。GPT-2 后来采用字节级 BPE，使任意 UTF-8 输入都可以退回到基础字节，而不需要普通的 `UNK`。

BPE 的训练过程可以压缩为四步：

1. 用 256 个单字节 token 初始化词表；
2. 统计训练语料中所有相邻 token 对的出现次数；
3. 选择频率最高的一对，创建表示二者拼接结果的新 token；
4. 将语料中这对 token 的非重叠出现合并，然后继续统计。

每轮合并会让词表增加一个 token。训练结束后必须保存两样东西：

- `vocab`：token ID 到原始字节串的映射，用于解码；
- `merges`：按训练先后排列的合并规则，用于编码新文本。

讲义用 `the cat in the hat` 做三轮训练。在它采用的并列频次处理顺序下，过程如下：

| 轮次 | 新 token | 序列长度 | 压缩率 |
| --- | --- | ---: | ---: |
| 初始 | 单字节 | 18 | 1.00 |
| 1 | `t + h → th` | 16 | 1.125 |
| 2 | `th + e → the` | 14 | 1.286 |
| 3 | `the + 空格 → the空格` | 12 | 1.50 |

这个例子还说明了两个容易忽略的事实：合并是非重叠的；空格也只是字节，因此完全可能成为 token 的一部分。之后编码 `the quick brown fox` 时，只能按已经学到的规则组合字节，不能根据新文本临时创造 token。

下面是一份刻意保持简单的训练实现。它展示算法本身，不包含大语料训练需要的数据结构优化：

```python
from collections import Counter


def merge_pair(tokens: list[int], pair: tuple[int, int], new_id: int) -> list[int]:
    """合并所有从左到右、互不重叠的目标 token 对。"""
    merged = []
    i = 0
    while i < len(tokens):
        if i + 1 < len(tokens) and (tokens[i], tokens[i + 1]) == pair:
            merged.append(new_id)
            i += 2
        else:
            merged.append(tokens[i])
            i += 1
    return merged


def train_bpe(text: str, num_merges: int):
    tokens = list(text.encode("utf-8"))
    vocab = {token_id: bytes([token_id]) for token_id in range(256)}
    merges = []

    for step in range(num_merges):
        counts = Counter(zip(tokens, tokens[1:]))
        if not counts:
            break

        # 次数相同时按 token ID 排序，保证结果可复现。
        pair = min(counts, key=lambda p: (-counts[p], p[0], p[1]))
        new_id = 256 + step

        vocab[new_id] = vocab[pair[0]] + vocab[pair[1]]
        merges.append((pair, new_id))
        tokens = merge_pair(tokens, pair, new_id)

    return vocab, merges


def decode(token_ids: list[int], vocab: dict[int, bytes]) -> str:
    raw = b"".join(vocab[token_id] for token_id in token_ids)
    return raw.decode("utf-8")
```

### 编码阶段为什么需要“合并顺序”

训练结束后，编码一段新文本仍然从 UTF-8 字节开始。每次查看当前相邻 token 对，只应用 `merges` 中存在的规则；如果有多个规则可用，优先选择训练时更早学到的规则，再继续合并，直到没有规则可以应用。

这也是一个常见错误来源：只保存“哪些 pair 可以合并”，却没有保存它们的优先级，会让编码结果与训练时不一致。

### 从课堂算法到可用 tokenizer

真正可用于训练的 BPE 还要处理不少工程细节：

- **特殊 token**：类似 `<|endoftext|>` 的边界标记必须作为整体保留，不能被普通规则拆开；
- **预切分**：GPT-2 风格实现会先用正则表达式划分文本，控制空白、数字和标点的组合方式；
- **文档边界**：统计 pair 时不能意外跨过本不相邻的样本；
- **确定性**：相同频次时需要稳定的决胜规则，否则词表无法复现；
- **性能**：每轮都重新扫描全量语料代价很高，需要增量维护计数和受影响位置；
- **流式训练**：语料可能远大于内存，读取与计数必须支持分块；
- **健壮性**：中英文、emoji、组合字符、空字符串和任意字节都应进入测试集；
- **往返测试**：至少持续验证 `decode(encode(text)) == text`。

字节级初始化解决了未知字符问题，却不自动解决特殊 token、边界和速度问题。一个“算法上正确”的 BPE 与一个“训练中可用”的 tokenizer，中间仍隔着完整的工程实现。

若希望跟着视频再实现一遍，讲义特别推荐 Andrej Karpathy 的 [Let's build the GPT Tokenizer](https://www.youtube.com/watch?v=zduSFxRajkE)。`tiktoken` 仓库也提供 `tiktoken._educational` 模块，可以训练一个小型 BPE 并逐步显示合并过程，适合用来核对自己的实现。

## 讲义链接延伸：真的可以不要 tokenizer 吗

第一讲列出了一组直接从字节建模的研究。它们不是简单地把 BPE 删除，因为字节序列往往长数倍；关键问题是如何避免让昂贵的全局模型在每个字节上都做同样多的计算。

- [ByT5](https://arxiv.org/abs/2105.13626)证明标准 Transformer 经过较少改动也能直接处理 UTF-8 字节。它消除了复杂分词流程，对噪声、拼写和发音敏感任务更稳健，但需要承担更长序列带来的训练和推理成本。
- [MEGABYTE](https://arxiv.org/abs/2305.07185)把字节分成 patch：全局模型处理 patch 之间的关系，局部模型处理 patch 内字节，从而降低长序列代价，并让同一思想扩展到文本、图像和音频的原始字节。
- [Byte Latent Transformer（BLT）](https://arxiv.org/abs/2412.09871)进一步让 patch 长度动态变化：下一字节越难预测、局部熵越高，就在那里切分并分配更多计算；可预测片段则合并成更长 patch。论文报告了最高 8B 参数、4T 训练字节的受控缩放实验。

三者共同指向讲义结尾的两个条件：模型仍需要在“块”这种抽象上计算，而且块最好能够随内容复杂度变化。BPE 预先用频率固定这些块；tokenizer-free 路线则尝试让模型或独立的 patch 机制在训练中决定它们。

## 怎样学习这门课

第一讲介绍的课程形式很值得注意：讲义本身是可以执行的程序，内容由 Python 生成并在浏览器中呈现。[官方讲义仓库](https://github.com/stanford-cs336/lectures)显示，运行 `python execute.py -m lecture_01` 会生成 `var/traces/lecture_01.json`，再由 edtrace 的浏览器前端展示代码位置、变量与渲染内容。它在传达一个信号——这不是只看幻灯片的课程，阅读、实现、实验和性能测量应当连在一起。

2026 版课程由五个单元和五次作业组成。作业不会提供一套只需补空的完整脚手架，而是给出接口适配与单元测试：先在本地完成实现，再到计算集群上测量性能；部分任务还会在固定预算下比较困惑度。评价重点因此不只是“答案是否正确”，还包括它是否高效、可复现。

自学者可以从[课程主页](https://cs336.stanford.edu/)获取讲义和作业。官方建议先在 CPU 上调通正确性，再按作业需求租用 GPU 做训练或性能测量，避免为空闲资源和低级错误付费；云算力价格会变化，因此这里不抄录讲义中的即时价格。

我会把第一单元的学习拆成下面几个可验证的小目标：

1. 从 UTF-8 字节实现 BPE 训练、编码和解码；
2. 用单元测试覆盖往返一致性、特殊 token 与确定性；
3. 实现 Transformer、交叉熵、AdamW 和训练循环；
4. 在小数据集上完成端到端训练，先确认 loss 能正常下降；
5. 记录吞吐、显存和训练 token 数，而不只观察最终 loss；
6. 再进入内核、分布式和缩放规律，解释瓶颈为什么出现。

课程允许使用 AI 作为导师式辅助，但不应把需要亲手形成的理解外包出去。对这门课而言，最有价值的结果不是“代码最终跑通”，而是能够预测它为什么会慢、为什么会错，以及怎样用证据改进。

## 我的理解

第一讲最重要的不是 BPE 的四步循环，而是它建立了一种看待语言模型的方式：**每个抽象层都在做资源分配。**

Tokenizer 决定一次注意力计算覆盖多少原始文本；数据管线决定哪些信息值得被看见；架构决定参数与激活如何使用；系统决定算力有多少真正转化为训练；缩放规律决定实验预算如何下注。把这些层连起来，才是“从头构建语言模型”的真正含义。

BPE 也不是最终答案。直接建模字节可以消除独立分词步骤，但现有 Transformer 在长字节序列上仍不够高效。未来系统或许会学习动态、分层的文本块；在那之前，BPE 仍是一个简单、稳定而且非常难绕开的基线。

第一讲到这里完成了课程地图和第一个基础部件。下一讲将进入 **resource accounting**：开始精确核算参数、激活、优化器状态、FLOPs 与硬件利用率。
